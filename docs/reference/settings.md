# Settings, engines and profiles

How settings, engine installations, configuration profiles, themes and languages behave. For a guided introduction, see the [user guide](../user-guide/README.md#9-profiles-and-settings).

## Settings and engines

**Settings** opens a dialog with **General**, **Appearance**, **Analysis**, **Playing**, **Board**, **Engines**, and **Profiles**. The **General → Language** menu lists Deutsch, English, Español, Français, Italiano, and Polski alphabetically. New installations default to English. **Board** offers previews of the built-in boards and local BGBlitz themes from `themes/*.zip`. **Apply** saves the draft and keeps the current category open. **Close** returns to the workspace. Closing the dialog, pressing Escape, or opening **Profiles**, **Manage opening books**, or **Open benchmark** with unapplied edits offers **Apply** (**Apply and continue** when another view opens next), **Discard draft**, or **Keep editing**. In the category list, Up and Down move to the previous or next category, and Home and End to the first or last. **General** holds the language, the player name and **My player profile**, the [virtual player profile](library.md#virtual-player-profiles) that stands for you in Study and the player database. Unlike the other fields, that choice belongs to the library rather than to the configuration profile, so it is saved with the player database and is the same in every configuration profile. **Playing** holds the bot engine and strength, the default play mode, **Open training analysis automatically**, game sounds and the bear-off direction. **Analysis** also offers **Open benchmark**. [Configuration profiles](#configuration-profiles)

Set a player name, default analysis depth (GNUbg 1–5 ply, default 3), separate playing strength (GNUbg 1–3 ply, default 1), and bear-off direction. New matches use the playing settings in effect at creation. Choose GNUbg or NeonGammon independently with **Analysis engine** and **Engine for future games**. NeonDojo accepts the `neongammon` **3.1.0** and **3.0.0** packages of the fork; the original Open Sage wheel and earlier `bgsage` 2.0.x builds are rejected. NeonGammon **3.1.0** is required for the named opponent presets (**Beginner**, **Casual**, **Intermediate**, and **Full Strength**, which plays checker moves at 3-ply and cube decisions at 2-ply) in **New match**; **3.0.0** remains supported for analysis and ordinary ply-based play. Under **Settings → Playing**, **Strength for future games** offers NeonGammon 1-ply, 2-ply (default when switching to NeonGammon), and **2-ply + Top-2 (10 mEq)** (`play_top_two`, stored in settings and the active configuration profile). **2-ply + Top-2 (10 mEq)** requires NeonGammon at 2-ply, cannot be combined with a named opponent preset, and re-evaluates the two leading checker plays at 3-ply in contact positions when they are at most 0.010 equity apart, leaving other checker decisions and all cube decisions at 2-ply. For analysis, NeonGammon supports 1–4 ply. The active profile saves the default playing strength. New sessions pin the bot, analysis and GNUbg rules installations separately. There is no automatic fallback to another engine. [Playing against an engine](playing.md#playing-against-an-engine)

NeonGammon requires a locked native ARM64 Python 3.12 environment. In **Settings → Engines**, enter that environment's `bin/python` path under **NeonGammon** and choose **Verify and save**. The backend checks package and model integrity (including `DifficultyPolicy` on `3.1.0`) and evaluates a position at 2-ply before enabling selection. The card shows the saved package version and verified depths, including 1-ply when its separate probe succeeded. The engine catalog supplies the supported analysis depths. If the installation becomes unavailable, the card retains the version and depths from its last successful check. Installation paths stay on the host. GNUbg handles MAT conversion and provides the play rules, dice, and SGF handling. NeonGammon makes bot decisions when selected. NeonGammon 1-ply requires a successful capability check with a bounded thread count. NeonGammon 3- and 4-ply are available for retrospective analysis and engine duels. New jobs and duels probe the requested profile before starting. [Local NeonGammon setup](../open-sage-local.md)

**Settings → Analysis** shows the **Analysis engine**, the **Default analysis profile** (depth), the **Error thresholds**, and the configured opening-book source. Set the four inclusive lower bounds in normalized equity loss. They must be strictly increasing, greater than zero, and at most one.

| Grade | Default threshold |
| --- | ---: |
| Questionable | 0.005 |
| Error | 0.020 |
| Blunder | 0.080 |
| Large Blunder | 0.120 |

The thresholds are part of the current configuration and can be saved in a profile. Applying changes updates the classification of existing analysis results from their stored equity losses. New matches capture the scale for feedback.

**Settings → Engines** (**Engines on this computer**) shows engine availability, the local installation paths, and the maximum calculation threads per engine, separately for analysis and for playing. The backend detects the logical CPUs available to its process and probes how many of those GNUbg accepts. The dialog offers whole-number overrides within the detected range, starting at 1 for GNUbg and 2 for NeonGammon, and labels each default choice with its thread count: **Default (1)** for GNUbg (both analysis and playing), **Default (4)** for NeonGammon analysis and engine duels, and **Default (2)** for NeonGammon playing. NeonGammon runs separate worker processes for playing, for hints, Coach and Tutor evaluations and Study answers, and for analysis, each behind its own lock, so a bot move, hint or Study answer does not wait for an entire game analysis block to finish. Each engine duel retains its own worker for each distinct NeonGammon profile (up to two) for the duration of a match or money block. GNUbg and NeonGammon draw from one CPU budget. On Apple Silicon the budget uses the performance-core count. Other systems use the parallelism available to the process. Background work normally leaves two cores available for playing, hints, practice and installation checks, or one core for background work on smaller hosts. A background profile wider than that allowance keeps its configured thread count and runs alone for the duration of its native evaluation or batch. The analysis value applies to new analysis jobs and duel series, the playing value to the bot of new play sessions. Analyses of a play session use the analysis value. Each job, session and series captures its thread counts when created. **Simultaneous analysis jobs** sets how many position, dice equity and match analysis jobs run at the same time on this computer, from 1 to 8 (**Default (1)**, saved per host). A change applies when the next job starts; running jobs continue. NeonGammon analyses share one general worker process, so at most one runs at a time while GNUbg jobs use the remaining slots. Additional jobs wait for their configured threads to become available. Engine duels and play sessions have their own workers and do not count. Remaining-time estimates come from benchmarks of a single job and can be too optimistic while several jobs share the CPU. Reference benchmarks retain their fixed thread counts, and their timings are only used for estimates with a matching thread count.

Automatic result readers stay within the selected analysis provider. Historical results and explicitly selected jobs retain their original provider and profile; copying a match retains completed results from both providers. NeonGammon results carry model and profile identity but do not claim GNUbg PR statistics.

The executable path is specific to the backend computer. Installation checks, analysis, playing, and benchmarks use the same resolution rules. An absolute path is resolved directly, a relative path containing a directory separator is resolved from the backend's working directory, and a bare name such as `gnubg` uses the first matching file on the backend's `PATH`. The backend reports an error if resolving or running that file fails. The resolved path must be valid UTF-8.

**Check installation** and saving a changed executable path check the version and run a real position evaluation within a single 10-second time limit. A failed check prevents an invalid path from replacing the saved installation. Installation settings use PostgreSQL revision checks. A concurrent change surfaces a conflict and retains the draft.

A new analysis job records its engine configuration and effective ply. Active-job deduplication includes the target, scope, ply, configured executable path, and version. An engine version change at the same path fails a job that expects the original version and preserves completed game checkpoints. A GNUbg dice equity job evaluates all rolls in one GNUbg run, checks the executable before and after that run and publishes no partial result, so a change during the job also fails it. Each such check compares the SHA-256 of the executable; a direct binary proves its version with its startup message, a wrapper script with `--version` before and after. Legacy jobs without a snapshot use the engine configured at backend startup. MAT imports use the currently saved executable path.

### Ply convention

NeonDojo stores, shows and compares every depth in the XG and NeonGammon convention: **1-ply is the raw neural-net evaluation**, and each further ply looks one roll ahead. GNUbg numbers the same raw evaluation 0-ply, so NeonDojo's 3-ply is GNUbg's native 2-ply. The backend converts only where it writes commands for GNUbg (`engine::gnubg_plies`), and converts depths that GNUbg reports back. A GNUbg 3-ply and a NeonGammon 3-ply duel side therefore search to the same depth.

Former migration 0079, now part of the [schema baseline](../development/architecture.md#database-schema), moved every stored GNUbg depth up by one level: saved settings and profiles, jobs and their results, match checkpoints, benchmarks, duel series, play sessions, flashcards and imported GNUbg SGF evaluations. The raw source tokens of imported analyses stay unchanged. Archived duel SGFs, and the player names and events read from them, keep the text written when the match was played. In duels from before migration 0079, a GNUbg side named `gnubg 2-ply` ran at today's 3-ply. Finished practice attempts, reviews and study-report snapshots also keep their recorded text. Flashcards exported to Anki before migration 0079 carry GNUbg's native numbering.

Former migrations 0019 and 0020 added GNUbg's native 3- and 4-ply analysis, today's 4- and 5-ply. Explicit profiles, existing jobs, and completed results retain their recorded depth. The requested depth is the GNUbg search profile, which allows early exit when the result is clear. Higher depths take longer, especially for full matches and dice distributions.

New GNUbg 3- and 5-ply analysis jobs save a checker move filter that sends up to the best 14 candidates from the 1-ply evaluation to 3-ply. At 5-ply it also sends up to the best 14 candidates from the 3-ply evaluation to 5-ply. Game and match analyses retain the actual depth of each exported candidate. Existing jobs keep the filter saved at submission or the GNUbg startup filter for older jobs.

## Configuration profiles

The header shows the active profile and marks it **modified** when your current settings differ from its saved values. Select a profile to switch or choose **Manage profiles** to open **Settings → Profiles**. Switching away from a modified profile asks first: **Save and switch** saves the current settings in the active profile before switching, **Manage profiles** opens **Settings → Profiles**, and **Discard and switch** drops the changes. Profile initialization warnings, unavailable resources and a failed switch appear as one warning badge with their count beside the profile; select it to read the details, and **Understood** dismisses the initialization warnings.

Choose **Show changes** in the profile menu to see each changed setting with its category, saved value, and current value. The arrow next to a current value restores that field from the saved profile and saves the current configuration. Related values such as a dice pair or a numeric or date range are restored together. The dialog shows any errors. The **modified** marker disappears after the last change is reverted. **Close** or Escape dismisses the dialog.

**Reset all changes** restores the entire saved profile in one operation after confirmation. **Cancel** or Escape dismisses the confirmation. A failed restore preserves the current configuration. After success, the changes dialog stays open with an empty list.

Profiles capture engines, default depths and error thresholds, playing and training defaults, language, sound, interface and board appearance, and opening-book references. **Settings → Profiles** shows the active profile and its change count at the top. Select a profile to compare it with the current configuration. Its full saved configuration can be expanded below the comparison. Profile timestamps use the app language and the browser's local time zone.

Each browser tab keeps its own database selection, search filters, sorting, Study deck, card-creation choices, and analysis filters. Table columns, column widths, and analysis board layouts are stored in the browser. Both sets of preferences survive reloads and profile switches. The browser uses legacy configuration values to seed these preferences once. Older profile files retain those values for compatibility. A removed database or deck is handled in the workspace that uses the selection.

**Apply** saves the current settings. To update a named profile, open **Settings → Profiles** and choose **Save in profile**. **Save as new profile** asks for a name, then creates and activates a profile. The **Profile actions** menu contains **Rename** and **Delete**. Activate a different profile before deleting the active one. **Restore saved profile** reapplies the active profile's saved values after confirmation. To save changes while switching profiles, use **Save and switch** in the header or in **Settings → Profiles**.

On the first launch after the profiles update, existing server and browser preferences are imported once into **Standard**. Profiles and current settings apply across the installation, including other browsers. On a version conflict, you can load the server version or save your local changes as a new profile. A recovery journal protects pending local changes.

Running analyses and matches retain their captured settings. If the profile cannot load, workspaces use the last confirmed settings or the built-in defaults. The profile controls report the failure and offer a retry. Engine installation paths are device-specific, and book files are stored as references. Activation checks the referenced resources and reports missing items. See the [original profile specification](../superpowers/specs/2026-11-10-profiles-design.md) and [implementation plan](../superpowers/plans/2026-11-10-profiles.md).

## Themes and language

### Board artwork

Under **Settings → Board**, choose a playing surface from the gallery. **Checker set** selects the checkers and their dice. **Doubling cube** selects the cube independently. Both menus offer the built-in and installed BGBlitz themes. **Match board** uses the selected board’s own artwork and follows subsequent board changes. An explicit choice stays selected when you change the surface. The large preview shows your combination immediately. **Apply** saves the combination as your current settings. To update the named profile as well, choose **Profiles → Save in profile**.

`npm run dev`, `npm run build`, and `npm test` in `web/` prepare artwork automatically from locally supplied BGBlitz archives. Preparation requires **Python 3.10+** and uses the original backgrounds, checker variants, dice, cubes and point-number strips. Because BGBlitz names its checker and dice sets "red" and "green" rather than by brightness, preparation measures the mean relative luminance of each set's opaque checker pixels and assigns the lighter set (with its dice) to White. Forest, Walnut, Slate, Moonstone, Viridian, Terra Rossa, Ion, Pelagic, and Carbon are built in and available without archives. The tracked `shared/configuration-options.json` lists the board themes that the backend accepts, and ordinary preparation only checks the archives against that list. It writes nothing but the untracked `web/src/generated-themes.json` and `web/public/themes/`. If an archive for a listed theme is missing, for example in a fresh checkout or worktree, preparation stops and names the missing ZIP files; copy or link them into `themes/`. To build without them on purpose, set `NEONDOJO_ALLOW_MISSING_THEMES=1`: the catalog then lacks those themes, and the list stays unchanged so the backend keeps accepting saved choices. Changing the list itself requires `--update-options`, which sets `board_themes` to the built-in themes plus the archives in `themes/`:

- **Add a theme:** place its archive in `themes/`, run `npm run themes:prepare --prefix web -- --update-options` and commit the updated list. Without the flag, preparation stops and names the unlisted archive.
- **Remove a theme:** delete its archive, run `NEONDOJO_ALLOW_MISSING_THEMES=1 npm run themes:prepare --prefix web -- --update-options` and commit the shortened list.

Restart the dev server after either change. [Board theme formats, sources and rights](../../themes/README.md)

### Interface appearance and language

Under **Settings → Appearance**, choose **Graphite**, **Club** or **Paper** and a **Light**, **Dark** or **System** display mode. System follows the operating system. On desktop, the interface preview updates to the right of the controls. Under **Settings → Board**, scroll the gallery on the left to browse artwork while the selected board stays visible on the right. Use **Apply** to save both previews. The browser applies its saved appearance before the first render. Tables, review sessions, dialogs and error messages use the same appearance.

Use **Apply** to save draft language and board settings. To discard a preview, choose **Close** and then **Discard draft**. NeonDojo localizes the interface, status messages, errors and number formats while preserving visible analysis, player names, filenames and GNUbg move notation. Native engine diagnostics accompany localized errors. Every message catalog is type-checked, and the test suite checks that each language has every key, the same placeholders and the plural forms it needs. Counted nouns use plural blocks such as `{count, plural, one {# card} other {# cards}}`; `web/src/shared/i18n/i18n-core.ts` chooses the form with `Intl.PluralRules`, and Polish supplies `one`, `few` and `many`. The translations are pending native-speaker review.

### Action icons and tooltips

The app uses a shared Lucide Outline icon set for actions such as saving, undoing, requesting hints, searching, and importing or exporting. Compact actions have localized accessible names and show tooltips on hover and keyboard focus. Key play decisions, **Undo step**, **Hint**, primary form submissions, and study actions also show text labels.

Tooltips stay above modal dialogs and remain visible when you move the pointer onto their text. Escape dismisses the tooltip and preserves the dialog's Escape behavior. The shared implementation lives in `web/src/shared/ui/action-icons.tsx`, `web/src/shared/ui/ActionButton.tsx`, and `web/src/shared/ui/useActionTooltip.tsx`. Action buttons preserve native submit and disabled behavior and forward refs. Export controls are download links.
