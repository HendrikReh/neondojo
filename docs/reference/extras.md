# Extras

How version information, engine benchmarks, engine duels and database backups behave. For a guided introduction, see the [user guide](../user-guide/README.md#8-extras).

## Version information

Open **Extras → Versions** for the running NeonDojo version with its build commit, for example `1.1.0 (b9bff70)`, and the availability and versions of GNU Backgammon and NeonGammon. **Technical details** shows the complete build commit and engine version output and, for a recognized NeonGammon release (`v3.0.0` or `v3.1.0`, identified by its runtime artifact fingerprint), a **NeonGammon source** link to its source commit. **Copy version information** copies the full report for troubleshooting. If some of the information cannot be loaded, **Try again** reloads only the missing part and keeps what is already shown.

`GET /api/version` returns the release version in `release` and the full commit ID in `commit`, or an empty `commit` when it is unavailable. The deprecated `version` field repeats the commit ID for earlier clients. `GET /api/engines` includes the repository and full source commit in the optional `fork` field.

## Engine benchmark

In **Extras → Benchmark**, choose a **Benchmark engine** and a measurement type, **Match analysis** or **Play-turn latency**. Each measurement type has its own history and comparison. GNUbg supports 1–5 ply; NeonGammon supports 1–4 ply after a capability probe. Depths initially come from Settings. The benchmark remembers depth selections separately for each engine while the app is open and flags an automatic fallback to a supported depth. Selected analysis depths run in increasing order in the background and continue when you leave the view. **Cancel run** also stops the active engine process. Other NeonDojo engine work waits while a benchmark is in progress, and a notice appears across workspaces. The app reads the benchmark status when it starts, when its window regains focus and after you start a run, and reads it again every two seconds only while a run is queued or running; an idle history is not polled. Other programs on the machine can still affect the measurement.

The fixed **WC2014 v1** reference is the 11-point match between Akiko Yazawa and Douglas Mayfield, with ten games and 460 checker moves. The app bundles an immutable copy of the unanalysed GNUbg SGF fixture, with a reference ID, version, and SHA-256 checksum. See the [fixture documentation](https://github.com/HendrikReh/neondojo/blob/main/backend/tests/fixtures/README.md) for provenance and reproduction. Existing evaluations are cleared before analysis.

**Total analysis time** sums the full analysis pipeline for each game, including process startup, loading, checker and cube analysis, and result preparation. Each game starts a fresh GNUbg process. The analysis is cubeful and deterministic, with zero noise and luck analysis disabled. The timer excludes waiting, the installation and version checks before and after each game, and database writes; the check that each game's GNUbg process is the pinned executable is part of the timed pipeline. **Ø analysis time / move** divides the total by all 460 checker moves, including forced moves. It represents the match-wide average. New GNUbg runs use `gnubg-match-v4-2ply-top14` at 3-ply, `gnubg-match-v4-4ply-top14` at 5-ply and `gnubg-match-v4-unlimited` at other depths. GNUbg protocol ids name GNUbg's native level ([ply convention](settings.md#ply-convention)). These protocols have no fixed per-game timeout. Older runs retain their recorded filter and timeout. Runs with earlier GNUbg protocols (`gnubg-match-v1`, `gnubg-match-v2-unlimited`, `gnubg-match-v3-…-top14`) timed a slower pinned-executable check; they stay in the history, are not pooled with v4 and no longer calibrate analysis time estimates.

**Measure play-turn latency** queues a separate run with the benchmark engine at the selected **Playing depth** (GNUbg 1–3 ply, NeonGammon 1–2 ply). The `gnubg-checker-turn-v2` protocol plays 11 fixed checker turns with dice already rolled, sampled from opening, contact, race and bear-off positions in the WC2014 reference. Each sample restores its own SGF checkpoint in a fresh process through the Playing adapter, plays one bot turn, and reads the resulting snapshot. The timer includes preparation, native process startup, checkpoint restoration, version guards, and result processing. Queue wait, installation checks, database writes, network time and animation are outside the timed scope. The history reports the arithmetic mean in milliseconds. Earlier `gnubg-checker-turn-v1` runs measured a slower pinned-version check and stay in the history without being pooled with v2. Play measurements use the same queue and cancellation controls. They are independent of analysis-time estimates and do not create games in the library.

History shows date, engine, depth, timing, and status, newest first. Select a column heading to sort by date, engine, ply, total analysis time (analysis only), average time per move or turn, or status; select it again to reverse the order. Times sort numerically, and runs without a measured time stay at the end in both directions. Status follows the run lifecycle: running, queued, completed, failed, cancelled. Equal values keep the newest-first order. Expand **Details** for hardware, the complete engine version and executable path, the reference, and the protocol. History is independent of library matches and profiles. To remove a finished run (completed, failed, or cancelled), select the trash icon in its row and confirm with **Delete**; **Keep** or Escape leaves it in place. Deletion is permanent and removes the run from the comparison. A deleted completed analysis run no longer calibrates [analysis time estimates](analysis.md#analysis-time-estimates); a running analysis keeps the average it started with. Queued and running runs have no delete action; cancel them under **Current runs** first. Backend restarts mark interrupted runs as failed. A new run starts its timing from the beginning. During a run, the engine availability indicator reuses the verified installation snapshot to avoid starting a competing probe.

| Method | Endpoint                      | Purpose                                                                             |
| ------ | ----------------------------- | ----------------------------------------------------------------------------------- |
| GET    | `/api/benchmarks/reference`   | Read the versioned reference and measurement protocol.                              |
| GET    | `/api/benchmarks/status`      | Read the active status shown in the global notice.                                  |
| GET    | `/api/benchmarks`             | List the latest 1,000 attempts, newest first.                                       |
| POST   | `/api/benchmarks`             | Queue attempts with a request such as `{ "engine_id": "gnubg", "plies": [1, 3] }`.  |
| POST   | `/api/benchmarks/play`        | Queue a play-turn run with `{ "engine_id": "bgsage", "plies": 2 }`. Without a body (or with `null`), the run uses the playing engine and depth from Settings; `Content-Type: application/json` is required either way. |
| POST   | `/api/benchmarks/{id}/cancel` | Cancel a queued or running attempt. Finished results are retained.                  |
| DELETE | `/api/benchmarks/{id}`        | Delete a finished attempt. Returns 409 for queued and running attempts.             |

Reference benchmarks always use fixed thread counts regardless of the overrides in Settings: 1 thread for GNUbg, and 4 threads for NeonGammon match analysis or 2 threads for NeonGammon play-turn latency. NeonGammon uses depth-specific `bgsage-match-v5-{depth}ply-4threads` and `bgsage-checker-turn-v4-{depth}ply-2threads-gnubg-rules` protocols. A fresh sidecar starts once per run and is then reused. Total elapsed time includes that one initialization plus the measured application pipeline; initialization is also shown separately. Each analysis game is an atomic block with complete installation verification before and after it; no result is returned or persisted before the final check succeeds. Individual requests retain their own boundary checks: they compare the file metadata recorded at the last complete verification and repeat the complete verification on any change. Hashes are reused only within one complete verification, never across them. Playing retains one GNUbg rule process from checkpoint inspection through action execution, then terminates it before committing the result. Playing timing includes preparation, SGF restoration and action execution. Historical results remain available and are grouped by their original protocol. Once three complete runs share the same machine, provider, full installation/model/rules snapshot, profile and workload, the view shows the median and minimum–maximum range of the three latest runs. The comparison shows the recorded thread count when known. Expand a group to see the engine version, the measurement protocol, and the GNUbg rules version for NeonGammon when recorded. Times measure application execution, not engine playing strength. Analysis time estimates for NeonGammon never use GNUbg timings.

Benchmark and Engine Duel workers retry transient database connection errors while their last confirmed 30-second lease is valid. The scheduler marks an expired benchmark as failed even when the queue is empty. It publishes no timing result.

The server creates all attempts for a multi-depth request together before starting them. New requests while a benchmark is running return HTTP 409. Unavailable engines and invalid depths return HTTP 422. OpenAPI documents the endpoints and types.

## Engine duels

Open **Extras → Engine duels** to see the selected series and its results. Select **New series** and choose the engine and **Playing strength** for **Engine A** and **Engine B**, the **Format**, a match length from 1 to 25 points, and up to 1,000 matches or pairs. GNUbg executes legal checker and cube actions and applies scoring and the Crawford rule. Each engine makes its own decisions. Both engines offer 1- to 4-ply for duels, GNUbg also 5-ply. The same number means the same search depth for both engines ([ply convention](settings.md#ply-convention)). NeonGammon requires a local installation that passes a real probe at the requested depth.

The default **Dice mode**, **Paired with sides swapped**, plays two complete matches per seed. The opening dice and the following rolls stay with their board sides when the engines swap. Each game number uses its own sequence, so a game ending early does not shift the dice for the next game. **Independent random rolls** uses a fresh sequence for each match. A blank seed under **Advanced** generates a fresh series seed. **Repeat series …** copies the configuration into the form so it can be run again. Exact replay also depends on the same engine installations and the dice protocol recorded with the original run.

Series keep running in the background. Each completed match is automatically saved under **Match database → Engine Duels** as the series advances. Its **Event** records both engines and strengths in series order, for example **Duel GNUbg 3-ply vs. NeonGammon 3-ply**. The same event applies to both legs of a pair. Replaying a seed creates new match entries. Existing series results stay in the series archive. Cancellation preserves completed results. If a worker loses its lease, the next worker continues from the latest saved game with the same seed. Download individual matches as SGF, or select **Analysis** in a result row to open the match in the Analysis workspace. Analysis opens the library entry with the identical SGF, also after it was moved to another database. If the entry was deleted from the library, or the match was played before automatic saving, NeonDojo saves it again under **Engine Duels** first (`POST /api/engine-matches/{id}/matches/{index}/library`). In paired mode the win rates count only complete pairs. From 20 complete pairs, a 95% confidence interval for A's match win rate is shown. Each pair mean (0, ½ or 1) counts as one observation, and the interval uses the Student t distribution with the sample variance of the pair means, clamped to 0–100%. That variance includes the variance reduction from swapping sides. If every pair has the same mean, the interval has zero width. A first leg without its return leg remains visible in the results.

Select a cancelled series and choose **Resume series** to put it back in the queue with its original engines, configuration and seed. After every verified game NeonDojo saves the score, played moves and captured engine evaluations. The worker resumes at the next game of the current match or block. An interrupted game starts again with its original dice. A series stopped before game checkpoints were introduced starts its unfinished match or block at game one. Previously archived results stay with the same series, including a completed first leg of a pair. The saved engine installations must still match the series settings.

Hover over a cancelled series to see the engines, playing format, dice mode, completed matches or blocks, and the number of games saved from the unfinished match or block. **Delete series** removes a stopped series from the history after confirmation. Archived matches and blocks stay in the Match database. If the current match or block contains saved games, NeonDojo adds those games to the Match database in the same transaction that removes the series.

**Live progress** shows the current match or block, the game within it, the provisional score in Engine A–B order, and an estimated remaining time for the series. During a money block the progress bar also advances with completed games. The score updates after verified games. The remaining-time estimate uses the current worker's elapsed time and newly completed games in money series or newly completed matches in point-match series, so it becomes available after the first such result and can vary with game length and machine load. Both legs count as their own match or block. Series statistics and library results use archived matches and blocks. A restarted worker measures a fresh pace.

**CPU time per move** shows each side's measured engine work, divided by that side's checker moves including forced moves and passes. CPU time adds up the work of all engine threads, so engines with different thread counts stay comparable. **Elapsed time** is the wall-clock time of the same decisions. Both include cube decisions. Process start, SGF replay, version checks and NeonGammon integrity checks are excluded: GNUbg is timed around each native bot turn (`nextturn`), so its values also include GNUbg executing the chosen move, a small but nonzero share; NeonGammon is timed around each evaluation in its worker. Matches played before this measurement have no cost data and are left out. The line **Matches with measurement** then shows how many counted matches are included. CPU time is the primary measure: GNUbg's elapsed time also contains roughly 12 ms of idle time inside each native bot turn, independent of depth. The values depend on the computer and its load. [CPU budget concept](../engine-duel-cpu-budget.md)

**Format → Money games without cube** plays blocks of independent money games instead of point matches. The cube is disabled, gammons and backgammons count, and the Jacoby rule does not apply. GNUbg plays with cubeless evaluation; NeonGammon uses its cubeless checker path, which evaluates serially and searches only its filtered top candidates at the full depth. **Games per block** (1–1,000, default 100) sets how many games one stored unit holds, and the count sets the blocks or block pairs, up to 1,000. For example, 500 block pairs of 100 games play 100,000 games. Each block is one native money session, archived as one entry under **Match database → Engine Duels** with the event suffix **(money, cubeless)**, so large series do not flood the library. Pairing works per block: both legs replay the same dice for each game number with the sides swapped. The result shows the game win rate, **Points per game for A** (−3 to 3) and the share of gammons and backgammons won. From 20 block pairs, or 20 blocks with independent rolls, a 95% interval for the points per game uses the Student t distribution over the per-pair or per-block means; choose the block size so that a series has at least 20 of them. GNUbg keeps the current game in one rules process and loads the preceding SGF checkpoint once when the next game starts. Each game verifies the scheduled rolls, the GNUbg installation and every participating NeonGammon profile before its result can enter the archived match or block.

New duels retain NeonGammon's checker evaluations from play, including up to five candidates, probabilities, depth and engine/model provenance. These appear alongside GNUbg's saved evaluations in Analysis and survive NeonDojo's SGF export/import. The NeonGammon values use the custom `BGTSC` SGF property; other SGF applications may ignore it. These are each engine's own playing evaluations, not a full match analysis by a common engine. Duels completed before NeonGammon evaluations were saved remain unchanged; select the duel in the **Match database** and use **Analyze selected matches …** to obtain a new analysis of both players.

## Database backup

Backups include saved engine-duel games from unfinished matches and blocks. NeonDojo also restores older archives created before migration 0099. Those archives resume at the next unarchived match or block.

On the source installation, open **Extras → Database backup** and select **Export backup**. The downloaded `.neondojo-backup` file (media type `application/vnd.neondojo.backup`) contains the PostgreSQL application data, including all match databases, original match files, import notes, user notes, completed analyses, saved positions, real and virtual player profiles, configuration profiles, preferences, benchmarks, engine duels and learning history. Derived read-model tables (`decision_index`, `decision_index_matches`, `native_analysis_revisions`, `imported_analysis_revisions`, `review_hits`, `review_hit_sets`) are omitted from the archive; restore clears them, writes the analysis revisions once from the restored analyses, and on-demand queries rebuild the decision index and review hits. The restore copies each table without its derived insert triggers: the archive already holds the player catalog and the played-record fingerprints, and historical job events are not announced to open job event streams. Foreign keys and other constraints stay enforced.

On the destination, open **Extras → Database backup** and use **Choose backup file** under **Restore backup**. NeonDojo checks the archive and compares its migration fingerprint with the destination database. The check uses a temporary upload and leaves the destination data intact. The consolidated schema baseline (`0001_schema.sql`) expands to match archives created against the equivalent earlier migration sequence (0001–0084), and migrations that touch only derived tables (such as `0089_decision_source_revisions`) are excluded from the fingerprint so earlier archives remain compatible. Migrations that change backed-up tables receive a new fingerprint and need an explicit restore conversion. For migration `0095`, NeonDojo also accepts the preceding archive layout (migrations `0088`–`0094`) and reads each game’s cube rule from its saved SGF during restore. The preview shows when the archive was created and how many library matches, saved positions, and flashcards it contains. If an older archive lacks a recorded creation time, NeonDojo uses a valid original filename (`neondojo-YYYY-MM-DD-HHMMSS.neondojo-backup`, UTC) and labels the time **from filename**. Damaged archives and incompatible schemas prevent confirmation.

A successful check enables **Review database replacement**. The confirmation dialog shows the creation time and compares the backup counts with the destination counts fetched when the dialog opens. **Difference** shows how many entries each category gains or loses after replacement: increases have a plus sign and appear in green, decreases have a minus sign and appear in red, and unchanged counts show a neutral zero.

**Replace database** overwrites the application data on the destination. Export its current database first if you need to keep that data. Benchmarks, engine duels, AI assessments and automatic Anki syncs are not stopped: while one of them runs, the restore answers at once (`409`) that the database is busy, names the running work, and you can retry when it finishes. Otherwise no new background work or analysis starts, and NeonDojo stops analyses running on the destination, including one that was just starting; each ends as `failed` with `Interrupted by database restore`, and its engine process is terminated. Requests still in progress then have up to 30 seconds to finish; meanwhile new requests are answered with `503`, and if the database is still in use afterwards, the restore answers that the database is busy. After confirmation, the backend checks the archive and schema again. PostgreSQL validates the data as the replacement is applied in one transaction. If restore fails, the previous data stays in place; analyses it stopped stay stopped and can be started again. Wait for the success message and select **Reload NeonDojo**.

The destination keeps its local engine installations, thread overrides, simultaneous analysis jobs limit, opening-book paths, and benchmark machine identity. Restore also rebinds opening-book paths inside restored configuration profiles and rebinds executable paths inside saved playing checkpoints to the destination's local installations so an archive cannot select an arbitrary program on the host. Queued and running jobs, benchmarks, AI assessments and engine duels from the backup end as interrupted by the restore. Automatic Anki review sync is switched off for every deck; enable it again with the intended Anki profile open. Saved playing checkpoints still require compatible local engine versions or models. Install external engines and opening books on the destination through their normal setup. The archive holds unencrypted data. It supports up to 16 GiB compressed and 64 GiB uncompressed. Large restores need temporary disk space for both forms of the archive.
