# Match library, positions and players

How match databases, imports, saved positions and the player database behave. For a guided introduction, see the [user guide](../user-guide/README.md#6-match-database).

## Match databases

**Match database** organizes named collections within a single PostgreSQL instance. Choose a database to filter the list, or choose **All databases** to search across the library. The selector beside **Import match** shows the import destination. It starts with the current collection when it accepts imports and otherwise uses **Unsorted**. Choosing another destination keeps the current collection open and applies to subsequent imports in the current app session. Multi-file imports process each file separately and report duplicates and failures per file.

NeonDojo automatically provides **Unsorted** for imports without an explicit target, **Bot Matches** for matches played against an engine such as GNUbg or NeonGammon, **Paused Matches** for resumable sessions, and **Engine Duels** for completed engine-vs.-engine matches. These system databases have fixed names and are protected from deletion. You can edit their descriptions. The sidebar tooltips for **Bot Matches** and **Paused Matches** show a localized default when the description is empty or repeats the database name. **Empty database** is available for **Unsorted**, **Bot Matches**, and **Engine Duels**. It requires confirmation and preserves saved positions and their relevant notes, flashcards and review history. NeonDojo rejects the operation if any of the database's matches has a queued or running analysis. **Paused Matches** is populated by pausing games in Playing. You can create, describe, rename and delete your own databases.

### Filtering and navigating matches

- The match list loads when you open **Match database**. It requests 50 results at a time and fetches another page when you select it.
- Use the search bar to find matches by player, file name, display name, event or round, or by the text of their tags and comments. **Filters** opens the advanced match filters, **Notes** searches tags and comments, **Position ID** finds exact board occurrences, and **Duplicates** opens the [duplicate match finder](#duplicate-match-finder). Opening a panel collapses the previous panel and keeps its inputs. The match list and the exact position search share the table filters.
- The advanced match filters cover player, match name, event, round, a date range on either the played or the import date, tag, comment, match type (match or money), result (completed, White won, Black won, draw, ongoing or unknown) and a range of match points.
- Applied table filters appear below the search field, even when the filter panel is collapsed. Remove a chip to rerun the search with the remaining filters.
- An exact GNUbg Position ID filter shows every occurrence as its own row in the match table, including repeats in the same game. Use the **Database**, **Game** and **Move** columns to locate or sort the occurrences. Click the move number to open that exact occurrence. The result count refers to occurrences. A checkbox selects the entire match, and the bulk action bar counts each selected match once.
- Select a single match and choose **Open match** above the list, or open it from a linked player name, by pressing Enter or by double-clicking the row. With a position filter active, this opens the exact occurrence. Use the arrow keys to move between rows.
- Sorting applies to all results before pagination. Click a data column header to sort ascending, then click again to sort descending. Names sort case-insensitively. IDs, PR, position counts, scores, game numbers and move numbers sort numerically. Scores sort by White, then Black. Missing values appear last in both directions. Changing the sort returns to the first page and clears the selection. Without a position filter, the occurrence-specific sorts fall back to import date.

### Duplicate match finder

**Duplicates** above the match table lists matches that occur more than once, in groups. It searches the selected database, or all databases under **All databases**. **Paused Matches** and the context of saved positions are not included.

- Two matches are duplicates when they have the same match length and every game has the same sequence of checker decisions: the board, the roll, the cube value and owner, Crawford and the score, each seen from the player on roll. The file format, file name, player names, metadata, notes and the order in which a source records the dice do not matter, nor does which side a source calls White. The same match imported as MAT, SGF and XG therefore forms one group.
- **Same moves** marks a group whose original files differ. **Identical files** marks a group whose members were all imported from byte-identical files, for example the same file in two databases. Within one database, the import already rejects an identical file.
- Each group lists its matches oldest first by **ID**, with database, format, import date, match length and analysis status. Click the match name or double-click the row to open the match.
- The checkboxes share the selection with the match table, so the actions above the list apply: for example **Delete**, **Move** or **Tags**. **Select copies** selects every match except the oldest of each listed group, up to 100 matches. Notes and analyses belong to their own match, so check which copy holds them before deleting the others.
- The list loads 50 groups at a time; **Show more groups** loads the next ones. A group lists up to 50 matches and names its full size. **Search again** refreshes the list; it also refreshes after an action in the library.

`GET /api/library/duplicates` compares a position fingerprint only for matches that share match length and position count with another match in the scope. On November 20, 2026, in a throwaway database with 10,200 synthetic matches and 2,034,800 positions, where every match shared both values with others and 200 groups of two were duplicates, `EXPLAIN (ANALYZE, BUFFERS)` measured about 1.7 s for the first page. On the local library with 128 matches and 24,221 positions it took 8 ms. These are PostgreSQL execution times, not API or UI latency.

### Table and metadata

The table uses the available width alongside the database selector and scrolls horizontally when needed. The default layout gives the two player columns equal room. Names can wrap to two lines in narrow columns, and the row summary shows the full names. The table shows PR, score, match length or money play, played and import dates, event, analysis status, tags and comments. **ID** is a stable match number. It survives a rename or move, copies get new numbers, and gaps are possible. REST uses the match UUID. **Positions** counts stored positions. The source format is available for import and export.

Use **Columns** to choose and reorder data columns, **Show all columns** to reveal them, or **Default columns** to restore the default layout. **Tournament** and **Comment** are hidden by default, and **Tags** is visible. The selection column stays available, and the table requires at least one data column. Hidden values remain searchable and are included in the row summary where applicable. The current sort is shown above the table if its column is hidden. Column visibility and widths are saved separately, and a hidden column retains its width.

Drag the right edge of a header to resize it, or focus the divider and use the arrow keys. Shift increases the step, Home and End jump to the width limits, and Escape cancels an in-progress resize. **Reset column widths** restores defaults for the current window, including the occurrence columns. Column widths are stored in this browser and the sort stays with the browser tab; neither follows the configuration profile. See [Configuration profiles](settings.md#configuration-profiles). Widths from the former notes column carry over to **Tags**. Each row has a shared hover summary with the match ID, players, match length, result, available PR, analysis profile and excerpts of tags and comments.

The metadata editor supports display name, played date, event, round, venue and result, with version checks. Player names and an optional display name identify the match in the table. XG and BGF imports retain the source event, played date, round, and location when supplied, and use the score after the last completed game. At startup, a bounded backfill fills missing match fields for older XG and BGF imports from the stored originals and corrects automatically derived results from them. It leaves matches with manual metadata saves unchanged, because an earlier manual save owns the entire metadata form, including empty fields. Stored positions, analysis, notes and learning progress are preserved. Money game results and results without reliable source data remain unknown.

The library shows PR for a complete match analysis with native GNUbg statistics. Individual game analyses appear as partial coverage. Native PR divides normalized equity loss × 500 by the number of unforced checker decisions plus close or actual cube decisions. GNUbg uses a different decision count from XG and BMAB. Older or incomplete results without qualifying statistics leave PR unavailable. [GNUbg match statistics](https://www.gnu.org/software/gnubg/manual/gnubg.html#gnubg-matches_review_stat_overall)

### Bulk actions and exports

Select matches with the checkboxes and choose an action in the toolbar above the list. **Open match**, **Resume match** and **Edit match details** require a single selection. **Copy**, **Move**, **Tags**, **Export** and **Delete** support multiple matches. Most actions support up to 100 matches. Exports support SGF and original format, with a limit of 50 matches and 64 MiB of combined source data.

**Analyze selected matches …** uses one engine and depth for the entire selection and submits one background job per available match. The dialog counts matches that cannot be analyzed and reports rejected submissions by match. **Try again** resubmits the rejected matches. **Bulk analysis** above the list counts completed analyses out of the accepted jobs for the selected database and shows failures separately, including after the dialog closes. **All databases** shows the combined progress, including older jobs tracked without a database assignment. The match list refreshes as tracked analyses complete. Reloading the Match database during a bulk analysis restores the list and resumes progress tracking in the same browser tab.

With a single available match, the dialog shows the time estimate before you confirm. If the dialog stays open until the analysis completes, Analysis opens on **Statistics** for that match. **Show results** does the same.

- Copies get independent match, position, game and move IDs, with copied tags, comments and all completed analyses with their original scopes and the selected analysis. Review history and active jobs belong to their original records.
- Moves preserve IDs. NeonDojo detects duplicates within a database by original-file hash. If the destination already contains that file, it retains both the existing destination record and the source match, including their notes.
- Deletion requires confirmation and skips matches with queued or running analyses. Saved positions and flashcards can still be used after their source is deleted.
- Exports return the original file or canonical SGF, with a ZIP for multiple matches. Use [Database backup](extras.md#database-backup) to capture the full library, including NeonDojo notes and review history.

The named collections, sortable tables and bulk actions draw on [ChessBase's database organization](https://en.chessbase.com/post/chessbase-18-tips-for-beginners-part-7-organising-databases). The position preview draws on its [database preview window](https://help.chessbase.com/CBase/16/Eng/preview_window_in_the_database.htm).

## Import formats

| Format | Support                                                                                                                                                                                                                                                                                                    |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.mat` | GNUbg converts Jellyfish MAT to SGF. The importer normalizes recognized resignation lines without shifting columns and expands compound bear-off moves into legal steps. It checks GNUbg diagnostics and replays the full move history before saving. The match date comes only from an `EventDate` header in the file; without one the date stays empty.                                                      |
| `.txt` | A plain-text match transcript in the MAT layout, as published by tournament archives. It takes the `.mat` import path and is stored as MAT under its original filename. A title box before the match length line is allowed. Other text files, such as GNUbg board exports, are rejected. |
| `.sgf` | Native UTF-8 parser for standard backgammon, including escapes, multiple games, setup positions, cube actions, scores, Crawford, Jacoby and move reconstruction. Ambiguous variation trees are rejected.                                                                                                   |
| `.xg`  | Native decoder for XG2 save versions 24–40. It checks the RichGame container and CRC, bounds Zlib decompression and converts to SGF. Supports inactive cube placeholders, open money sessions, compact checker notation and valid in-progress point matches, including an explicitly unfinished last game. Every recorded position must follow from the replayed plays. |
| `.bgf` | Native Rust decoder for BGBlitz BGF 1.0 with a JSON header and JSON or Smile payload, optionally Gzip-compressed. It preserves checker moves, forced passes, double/take/drop actions, colors, scores and Crawford or Jacoby rules, then replays the resulting SGF.                                        |
| `.ogxm` | Native import of HedgeHog OGXM v2 match files, including archive exports. Keeps the played line, scores, match metadata, and available checker and cube evaluations with their original units and provenance. No external codec or engine is needed to import. |

Transcribed XG matches can contain irregularities that XG keeps. The importer resolves three of them and lists each one with the import result:

- **Illegal move.** XG marks a played move as illegal but keeps the position after it. The import continues from that position. The move is not stored as a checker decision, and its XG checker and no-double analyses are not imported.
- **Recorded starting position.** A game that starts mid-game, with or without an edited first move, starts from its recorded board and cube. The game's statistics then cover only the recorded moves.
- **Unfinished game.** A game marked as in progress is followed by the next game. The game keeps its moves but has no result; the next game's header provides the score.

Transcribed MAT and `.txt` matches can contain wrong moves and scores. The importer keeps the match and lists each resolution with the import result:

- **Illegal or unreadable move.** GNUbg cannot play or read a move, for example `21: 24/20`. The game ends before that move and keeps the moves before it. The note names the game, the move number, the line in the file and the move text. If the next game's header establishes an award, the game shows it as a recorded result without a winning type; later games are imported from their own headers. Because GNUbg continues after such a move with a position the file never had, the importer locates the first rejected move by validating ever shorter prefixes of the file. The original file stays unchanged.
- **Score mismatch.** A game header's score differs from the previous game's result. The recorded header score is used, because GNUbg and the match context take it from there.
- **Unfinished game.** A game without an ending line is followed by the next game. The game keeps its moves but has no result.

A file whose games cannot be read at all, a game header that cannot be read, a file without any legal checker move, or errors in more than 20 games are still rejected.

The notes are saved with the match and kept with its copies. They appear as **Import notes** above the match or game comment in **Notes**, the analysis header shows their number, and the match database marks the PR of these matches with a warning sign. Analyses and statistics cover the imported moves only; a game ended early has fewer decisions. Matches imported before this check have no saved notes.

The XG importer rejects XG1, later edits within a game, other invalid-marked moves, automatic doubles, unanswered doubles, beavers, raccoons and other variants. BGF variants, custom starting positions and restricted cube rules are also rejected. XG candidate and cube evaluations, depth labels and rollout references, and supported BGF analysis are stored as source analysis. The original artifact retains full XG rollout streams and comments. NeonDojo does not interpret XG RTF comments. [Import fixtures and format references](../../backend/tests/fixtures/README.md)

OGXM import supports standard match and money play. It replays the recorded moves, validates the final score and checks a supplied CRC32 or SHA-256 digest. OGXM v1, `.ogxms` streams, standalone analysis files, variants, custom setups, and special actions such as beavers and settlements are unsupported. The original file retains annotations, signatures, clock/video data and other source data; NeonDojo does not display them or verify signatures. Imported OGXM evaluations are visible as source analysis; they do not count as local GNUbg analysis or feed recurring-mistake statistics. When an OGXM export stores only summary values for a checker move, the selected imported analysis shows the recorded best equity and loss where available, labels the unit as unknown if the source omits it, and shows known legacy HedgeHog zero placeholders as **Not evaluated**. [HedgeHog format and codec](https://hedgehog-bg.com/community)

An upload takes one file and has a **16 MiB** limit including multipart framing. SHA-256 detects identical files within the target database. The original, canonical SGF and position records are saved in one transaction. Parsers and archives have separate size and record limits. Filenames and file contents are handled as data.

## Saved positions and searches

In **Analysis**, choose **Save position** to add the specific pre-move decision and its match context to **Positions**. The collection starts empty and fills through explicit saves. **Remove from collection** works for individual or selected entries. The row's remove icon appears for the row under the pointer, the row with keyboard focus and the previewed row. After a removal, **Undo** above the results puts those positions back. A saved decision can survive deletion of its source match or database, retaining player, roll, score, original match ID, related notes, and position analyses. It can still be analyzed, annotated, and used for study or Anki. Full game and match analysis and original-file export require the source match.

Use **All analyzed decisions** above the collection to search every checker and cube decision of one player in the displayed analyses, whether or not the position was saved. Choose the player, then combine database, decision type, error type, game plan, an equity-loss range, the points the player and the opponent still need, cube value and cube owner. The search uses the same filter card as the collection: player, database, decision type, error type and the loss range sit in the search row, the remaining fields under **More filters**. Until a player is chosen, a note beside the search button says so. Results are paged on the server and show the score as away values, the cube, the played and best action, the loss and the analysis source. They start with the largest loss; the **Loss** heading reverses the order. Click a row or move with the arrow keys to preview the board with its cube context. Enter, a double-click or **Open in Analysis** in the preview opens the decision in Analysis: a checker decision at its position, a cube decision in its game with the cube evaluation selected. Only a checker decision has a stored position and offers the save button for the collection. Filters, results and the chosen row stay in place while you visit the saved positions. Choose **Practice results** to practice up to 20 errors of the current page in the recurring-mistakes dialog. `GET /api/study/decisions` supplies the list from the decision index described under [My recurring mistakes](study.md#my-recurring-mistakes). The filters and the page are evaluated in PostgreSQL; `direction=asc` or `desc` orders by loss, and both orders follow the `decision_index_player_loss` index, ascending by reading it backward. On November 16, 2026, in a throwaway database with 400,000 synthetic decisions (53,735 matching one player's default loss filter), `EXPLAIN (ANALYZE, BUFFERS)` showed a forward index scan for the first descending page (0.3 ms) and a backward scan for the first ascending page (0.2 ms) and for ascending page 100 (8.3 ms). These are warm PostgreSQL execution times, not API or UI latency.

The position table has a fixed preview area on the right. Click or use the arrow keys to select a row, then press Enter, double-click, or use **Open analysis** next to the preview title to open the exact decision; the icon beside it finds similar positions. The preview grows with the window. Equity loss, decks, tags and notes show below the board. Expand **Source and position details** for the originating database, checker position ID, match length, event and round. The number of matching positions stands beside the page title. The table has its own sort and column widths. Its row tooltip gives context and analysis provenance. The sortable **Decks** column shows deck names alphabetically. Equivalent decisions share deck membership when the checker arrangement, roll, score, and cube context match. Membership updates across loaded pages and in the preview after adding positions to a deck.

The default columns show match, game, move, player on roll, dice, score and equity loss. Use **Columns** to show or hide fields, reveal all selectable columns, or restore the default selection. Column choices are stored in this browser, and hidden columns retain their widths. **Show played moves** controls the recorded move independently. When the current sort column is hidden, the toolbar shows the sort and its direction.

Filter by database, search text, player on roll, match name, event, round, exact tag, comment, checker position ID, match points, roll, score, Crawford, cube value, local analysis, or native equity loss. One die matches either die in the recorded roll. A pair matches either order. For example, to see how Mochy played a specific position, combine **Player on roll** with the checker position ID and roll. **Show played moves** adds the recorded decision to the table and preview. It starts off so answers stay hidden during study.

Applied filters appear below the search controls, including when **More filters** is collapsed. Removing one applies that change immediately. Choose **Search positions** to apply edited fields. **More filters** groups the fields by **Match**, **Position**, **Analysis**, and **Tags and comments**; value ranges and the two dice sit side by side. Sort with the column headings; a saved search keeps its sort and direction. After **Delete search**, **Undo** saves the search again under the same name. If a search has no matches, **Show all saved positions** clears its filters.

Results retain the full GNUbg position and match IDs. Comment filters consider the match, the relevant game, the position, and the matching checker move. Selected-analysis loss values show their actual engine and depth, with unavailable evaluations shown as unknown. The collection searches checker decisions. Use **Statistics** or **Cube and move notes** to review cube decisions.

Saved imported decisions are validated once into a derived index before filtering and pagination. Older libraries are prepared in bounded batches (16 source catalogs or 2,000 decision records per request); if preparation is still pending, narrow the database or retry the search. The index records the validation-rule and match-source revisions. Original records remain unchanged.

**Saved searches** in the search row loads a named search as soon as you choose it. The three-dot button beside it opens **Save current search…**, **Delete search** and a reload of the list; the save dialog stores a new search or updates and renames the loaded one. PostgreSQL stores the filters, sort, direction, and revision. Concurrent edits return HTTP 409 and preserve the draft. A search referencing a deleted database flags the missing database. The numbered navigation jumps within the current search, including directly to its first and last pages. The board previews the first result when another page loads. Checkbox selections carry across pages. Returning to the workspace keeps the current page, selection, and preview in place while refreshing.

The checkbox in the table header selects the current page. Select up to 200 positions to show the selection count, **Add to deck**, and **Clear selection** in the toolbar above the table. The three-dot button opens **More selection actions** next to the selection controls and contains **Remove from collection**. The add dialog checks how many positions have a usable answer in their selected analysis. Its add button shows the number ready for transfer. If none are ready and a selected position needs analysis, **Open analysis** opens the first such position and keeps the selection for your return. The transfer reports each position as added, updated, already in the deck, requiring analysis, or unavailable. Study answers require a validated result from the selected analysis, including comparable imported checker analysis. Missing numeric depth remains unknown. Existing cards retain their saved solution and provenance; explicitly adding an existing question may refresh its solution while preserving review history. Identical questions share FSRS review history. After a transfer, **Study this deck** beside the outcome opens a fresh study view of the receiving deck. Choosing decks and the Anki export live in **Study**. A deck can hold 1,000 cards. If a batch would exceed that limit, the entire batch is rejected.

## Similar positions

In **Positions**, the icon beside **Open analysis** in the preview, **Find similar positions**, opens **Similar positions** for that checker decision. The heading names the source match, game and move. **Back to saved positions** returns to the collection.

The search ranks checker occurrences across the library by how far their boards are apart. The distance is the smallest number of checker-pips needed to turn one arrangement into the other. For each side it compares how many checkers lie beyond each point, from the bar down to the 1-point, so a checker on the bar or one already borne off counts at its full distance. Boards are compared from the perspective of the player on roll, so the same arrangement with the colors reversed has distance 0. The result holds up to 50 occurrences, nearest first, with 25 per page.

By default the search leaves out the other occurrences in the source match, its copies and other imports of the same original file. Positions from an unfinished Competition match are always excluded, and searching from such a position is rejected. These options narrow or widen the search:

| Option | Effect |
| --- | --- |
| **Same dice** | Keeps occurrences with the same unordered dice pair. |
| **Same match score** | Keeps occurrences with the same match length, the same score from the mover's perspective and the same Crawford state. For a money-game source the option is **Money games only** and keeps money games. |
| **Same cube value and owner** | Keeps occurrences with the same cube value and the same ownership relative to the player on roll. |
| **Include current match** | Adds the source match and its copies. |

The table shows the match, the player on roll, game, move, the score as away values from the mover's side or money game, the cube value and owner, the played move, the loss and the distance. The loss comes from the match's displayed native analysis and shows a dash without one. Select a row to preview its board. **Open analysis** opens that occurrence in Analysis.

### Practice similar positions

**Practice results** opens **Practice similar positions** with every result of the current search, in list order. Each question names the match, game and move and shows the match length or the money-game Jacoby setting.

- Play a complete checker move and choose **Check my move**. GNUbg evaluates the position at the default analysis depth from **Settings → Analysis** and returns the best play, your move, both equities and the normalized equity loss. Scoring saves no analysis job and leaves the displayed analysis unchanged.
- **Reveal answer** shows the best play from the match's displayed analysis without scoring it. It reports an error if that analysis has no supported checker answer for the position.
- After a check, **Your move** and **Best play** switch the arrow preview on the board.
- **Next**, or **Finish** on the last question, moves on. While a check is running, the same button is **Skip position**. Skipped and revealed positions are not scored.

Scoring and revealing are rejected while the source match is an unfinished Competition match. When the round ends, it shows the average equity loss of the scored moves and how many positions were scored. **Retry missed moves** starts a new round with every scored move that lost equity.

A round with at least one scored move is saved as a summary with its completion time, number of positions, scored moves, moves with a loss, total loss and whether it was a retry. The individual positions and moves are not stored. If saving fails, **Retry save** sends the same round again. Repeating a save with the same summary is safe, and a different summary under the same round ID returns HTTP 409.

**Study → Practice history** lists the saved rounds in their own section, newest first, 25 at a time, with **Load older rounds**. Each row shows the completion time, **Practice** or **Retry**, scored moves out of positions and the average loss. The chart plots the average loss of each round over time and marks retries separately. Its trend line is a rolling average of up to 5, 10 or 20 practice rounds, without retries, and appears from the second practice round. Left/Right and Home/End move between the rounds in the chart.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/positions/{id}/similar` | Up to 50 nearest checker occurrences. Optional `same_dice`, `same_score`, `same_cube` and `include_current_match`. |
| POST | `/api/positions/{id}/practice-score` | Score a complete checker move given as up to four `steps`; an empty list is a forced pass. |
| POST | `/api/positions/{id}/practice-answer` | Reveal the best play from the displayed analysis. |
| GET / POST | `/api/study/similar-practice` | List saved rounds with the `before` cursor, or save a round summary under its stable `id`. |

## Player database

Open **Player database** to find players by display name or imported alias. Your NeonDojo bot matches appear there too: the human side is a NeonDojo player under the player name you played with, and the engine side has no profile. The result table shows match and game counts. It starts with the players who have the most matches and shows the first profile until you select another. Click a column heading to sort by name, matches or games, and click it again to reverse the order; match and game counts start with the highest value, and players with equal counts follow by name. `GET /api/players` takes the same order as `sort` (`name`, `matches`, `games`) and `direction` (`asc`, `desc`); an `after` cursor continues the default name order only. When an alias accounts for a hit, its name and source appear under the player name. When several listed profiles share a display name, for example the same username on Galaxy and OpenGammon, each row shows its platforms under the name, and `GET /api/players` returns them in `name_platforms`.

Select a row to see the profile and its matches alongside the results; both tables scroll independently. The profile header lists the player's other imported names and shows the PR per analysis profile above the matches; the analysis depth is visible, and the tooltip names the full engine profile. The match list shows the opponent, the score with the player's points first, the player's PR in that match, the match format, event and round, database, date and game count. Missing values show as a dash. Filter the matches by database above their table and change pages below it. Click a match row, or press Enter on it, to open the match; click the opponent's name to switch to that player's profile.

Below the matches, from two fully analyzed matches on, the profile shows a chart of the PR per match with the average of the last ten matches, weighted by rated decisions. Dashed lines show the same average for checker play and for the cube. The checker value divides the saved checker losses by the unforced checker plays; the cube value divides the remaining loss by the close cube decisions.

While matches of the profile have no PR, **Analyze unrated matches …** next to the rating collects those without a queued, running or completed analysis and opens the analysis dialog of the match database, where you choose the engine and depth before any job starts.

Choose **Edit** to change the display name or add an alias for future imports; **Save** stores both. Galaxy, OpenGammon and NeonDojo names have separate platform scopes, so a bot-match name never merges with an imported name of the same spelling, and an alias from another source is listed by its name alone. **Merge …** opens with the search field focused and, until you type, offers profiles that contain the first word of the current display name. Select one to see the retained and absorbed profiles side by side with their aliases and match counts. Confirm to assign the absorbed profile’s aliases and matches to the retained profile. The absorbed profile disappears from the player list. Match records retain their stored names.

### Virtual player profiles

A virtual profile groups real profiles without changing them, for example the same person's Galaxy, OpenGammon and NeonDojo players. It never owns matches of its own; its matches are exactly its members' matches. Unlike **Merge …** it is reversible: the members keep their aliases, names, matches and their own rows in the player list, and they can be removed again at any time. The row of a member names its virtual profile under the player name, and the member's profile header links to it as **Part of**.

**Virtual profiles** above the player search lists every virtual profile with its match count; **My profile** marks the one chosen in Settings. **New virtual profile …** asks for a name, which must be unique regardless of case. Select a virtual profile to see it in place of a real profile: **Add member …** searches the real profiles and adds the selected one, the member list shows each member's aliases with their platforms and its match count, and **Remove** takes a member out. **Rename …** and **Delete …** change or remove only the group; deleting it leaves its members, matches and analyses unchanged. A real profile belongs to at most one virtual profile, so no match counts twice; adding a profile that belongs to another group asks you to remove it there first.

The virtual profile shows the same consolidated results as a real profile: the PR per analysis profile from the fully analyzed matches of all members, the matches of all members with the group's side, the opponent and the PR, and the PR chart. A match between two members lists both sides.

**Settings → General → My player profile** chooses the virtual profile that stands for you. It opens first in the player database and is the default player in Study, **My recurring mistakes** and **All analyzed decisions**. Your bot matches count for it once your NeonDojo player is a member; a new player name in Playing creates a new NeonDojo player, which you add the same way. Bot matches enter a PR, of a real or a virtual profile, only when played in Competition mode without learning aids and once they are finished; matches played with Training, Coach, Tutor or a hint, and running Competition matches, appear in the match list without a PR contribution. The coverage beside the PR counts only matches that can enter it, and **Analyze unrated matches …** leaves the other bot matches out.

When **Merge …** absorbs a member, the retained profile takes over its virtual profile if it has none; otherwise it keeps its own, and the absorbed matches count there. Real profiles are only removed by merging, which removes their membership with them.

`GET /api/virtual-players` lists the virtual profiles with `match_count` and `rateable_match_count`, the matches that can enter the PR, and `GET /api/players/{id}` reports the same `rateable_match_count` for a real profile. `POST /api/virtual-players` creates one, and `GET`, `PUT` and `DELETE /api/virtual-players/{id}` read, rename and delete one. `POST /api/virtual-players/{id}/members` adds a member, and `DELETE /api/virtual-players/{id}/members/{profile_id}` removes one. Every change takes the expected `version` and answers a stale one with 409. `GET` and `PUT /api/virtual-players/me` read and set **My player profile**. `GET /api/library/matches?virtual_player_id=` lists the consolidated matches, and `GET /api/players` names a member's group as `virtual_profile`. The schema baseline `0001_schema.sql`, which includes the former migration `0084_virtual_player_profiles`, holds the tables and the view `virtual_player_sides`, the single definition of which match sides belong to a virtual profile; backups include the groups and their members. Migration `0085_bot_match_players` catalogues the human side of bot matches under the `neondojo` platform, adds the view `player_match_sides`, which defines a real profile's sides and which of them can enter a PR, reduces `virtual_player_sides` to the members' sides, and adds the existing NeonDojo players to **My player profile**, so earlier results stay the same.

PR is shown by analysis profile. NeonDojo uses complete, compatible match analyses and divides total normalized equity loss by the total number of rated decisions, using the same PR scale as the match database. Each value shows how many of the player’s total matches contributed to it, with the analysis profile beneath the value.
